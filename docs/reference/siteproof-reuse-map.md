## Important findings from the donor implementation

### Challenge engine

SiteProof keeps challenge selection on the backend, issues one short-lived challenge at a time, uses a cryptographically random nonce, and does not reveal the future sequence. `INCONCLUSIVE` is treated as a legitimate outcome and may consume a bounded retry budget. NirikshanX should preserve these trust properties while using PWA-appropriate challenge categories.

### Evidence integrity

SiteProof packages evidence objects with exact sizes and SHA-256 values, then independently hashes uploaded bytes on the server. NirikshanX should preserve the rule:

```text
client-declared hash + server-computed hash -> must match before acceptance
```

Accepted evidence becomes immutable; corrections create new records/events rather than mutating the original evidence bytes.

### Inspection state machine

SiteProof exposes dedicated commands (`assign`, `acknowledge`, `mark ready`, `cancel`) instead of accepting arbitrary status values. Assignment history is append-oriented and audit events are written in the same business transaction. NirikshanX should retain that discipline but implement its broader lifecycle.

## What SiteProof does not solve for NirikshanX

NirikshanX still needs its own architecture and domain model for:

- government hierarchy and jurisdiction;
- institution/scheme/project management;
- six-scope RBAC + ABAC;
- surprise inspector candidate generation and exclusion reasons;
- unified offline PWA;
- CCTV device/health/occupancy intelligence;
- attendance ingestion and contradiction analysis;
- explainable risk snapshots;
- corrective actions;
- national/state/district reporting;
- human-in-the-loop AI governance.

## Rule for future ports

Before porting any SiteProof code:

1. identify the exact trust property or algorithm being reused;
2. document the source path and assumptions;
3. write NirikshanX acceptance tests first;
4. adapt to NirikshanX domain types and security model;
5. remove Android-/organization-specific assumptions;
6. preserve attribution/license obligations where applicable;
7. verify that the resulting behavior is still explainable and auditable.
